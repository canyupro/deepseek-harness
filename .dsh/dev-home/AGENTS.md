# 用户全局偏好

本文件是跨项目的全局通用规则，不绑定具体使用场景。项目级 `AGENTS.md` 定义具体工作区的规则；两者冲突时以项目级为准。本文件不覆盖 system、developer 和直接用户指令。

## 语言

1. 始终用中文回复；代码注释也用中文书写。项目若另有语言约定（例如英文源文档配中文镜像），以项目约定为准。

## 回复风格

2. 先给结论，再展开解释。
3. 多用列表、要点和表格，避免大段文字堆砌。
4. 解释技术问题时，尽量结合具体例子。
5. 信息粒度对齐：不确定用户想要多详细时主动对齐——用户说得笼统（如“帮我看看这个项目”），就先给概览或先确认方向，别过度深挖；用户说得具体（如“改第 5 行，把 x 改成 y”），就按同样具体的程度回应，别小题大做；实在判断不了就直接问一句想要多详细。

## 工作流习惯

6. 动手修改代码前，先简述思路和影响范围。
7. 提交信息遵循 Conventional Commits 规范。
8. 涉及删除或覆盖已有文件时，先展示目标内容再执行。
9. 复杂任务先拆解为任务清单，逐项完成。

## 验证与复盘

10. 实践是检验真理的唯一标准：任何推断、边界、机制的真实行为，都必须实测验证后才能作为结论，不靠文档推断或想当然。
11. 复盘与改进遵循「收敛 → 发散」两步：收敛，把具体教训提炼为泛用规则写入持久记忆，使其适用于所有场景而非仅当下项目；发散，把改进项按适用分类逐一落地，先小样验证再批量，命名与格式以本机实际行为为准，不盲信文档示例。

## 共享记忆（与其他 CLI 共用）

12. 共享记忆目录：`~/.agents/memory/`（`MEMORY.md` 是索引，其他 md 是记忆条目）。zcode、Codex 与本 harness 共用该目录。
13. 本 harness 不会自动加载该目录，因此**每次会话开始先读 `~/.agents/memory/MEMORY.md`**，再按需展开其中指向的条目。
14. 新增长期记忆时**双写**，保证两侧一致、避免分叉：条目文件与 `MEMORY.md` 索引同时写入共享目录 `~/.agents/memory/`；当前工作区若已约定自己的记忆目录（例如 AIGC 的 `<repo>/memory/`），同一份内容也写进去，并在共享索引留一行指针。工作区没有这种约定时，项目专属事实仍写成带项目名的条目放在共享目录，不必复制全文。

## 委派与组队：subagent vs Agent Teams

### 判据：先看通信拓扑

- 需要**成员之间横向说话**（A 问 B、B 回 A、peer 复核）→ 用 Agent Teams。
- 需要**依赖排序**（T2 blocked_by T1）或**写作用域登记** → 用 Agent Teams。
- 只是"我派活、手下交结果"（纵向、一次性）→ 用 `subagent`。
- 两者都不需要 → 自己做。

一句话：**需要"另一个成员给它递话"才用团队；否则 `subagent`。**

### 硬规则

- `spawn_teammate` **必须用户明确要求**才能调用（策略固定文本，不可配置）；`subagent` 无此门槛。
- **并行 ≠ 组队**：并行取证、抓数据、跑脚本用 `subagent` 扇出。
- 团队每个成员的每次请求都额外携带策略文本 + 9 个工具 schema；能扇给 `subagent` 的不要拉成团队。
- 团队成员**创建后路由固定**（写在 descriptor 里），改配置不影响已有成员。
- teammate **名字永不复用**；成员闲置时先 `send_message` 唤醒，**不要新建**。

### 团队纪律

1. 任务板先行：`team_task_create` 写清 `write_scopes` 与 `blocked_by`，再 `spawn_teammate`。
2. 一人一个文件 / 一段写作用域，**不得重叠**（`write_scopes` 只是警告，不是锁）。
3. `wait_agent` 之后必须重新 `list_agents` + `team_task_list`；`inactive` ≠ 完成。
4. 依赖就绪后主动 `send_message` 唤醒 owner（任务就绪不会自动唤醒任何人）。
5. 成员长时间无产出：先 `send_message` 要一句进度，再决定是否 `interrupt_agent`；不要直接判定卡死。
6. 收尾自己做：审 diff、跑测试、给结论（细节可委托，验证不可委托）。
7. **Lead 的 `todo_write` 必须与团队任务板同步**：每次任务状态转换（claim / complete / reopen / 重派 / 收口）后立即刷新自己的 todo。两者性质不同——`todo_write` 只是 Lead 的私人进度条，**不参与交付判定**；团队任务板（`team_task_*`）才是权威记录。不同步会让界面进度与板上状态互相矛盾，误导成员与用户（用户的分辨依据应是 `task-N` 编号，而不是带圆点的进度条）。

### 路由与成本

- 需要显式选模型时，优先用配置里的默认路由；只有任务确实需要才点名按量计费的强模型。
- 具体模型名以**配置**为准（`<项目根>/.dsh/team.json` 里的成员路由，或配置里的路由设置），不要写死在提示词或技能里。

### 长期组织（硬门禁）

- 用 Agent Teams 时**必须**按技能 `agent-team-roles` 组织：调研 → 施工（≥2，写域互斥）→ 测试 → 验证 → 监督，五类报告齐备。
- 团队编制放在 `<项目根>/.dsh/team.json`，用 `spawn_team` 一键建队。
- **不得把某个任务的文件清单、结论或一次性排查过程写进编制或技能**；任务只作为验证案例。
- 总协调不得绕过测试、验证、监督直接宣布完成。

### 反模式

- 用团队做一次性调研；用 `subagent` 做多阶段协作；把并行当团队。
- 成员闲置就新建（名字不复用，应唤醒）；同时用两条通道干同一件事。
- 把 `todo_write` 当成交付记录或审计线索（它只是 Lead 的私人进度条；权威记录是团队任务板）。
